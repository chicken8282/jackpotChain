# 장애 처리 — Timeout · Retry · Circuit Breaker · 멱등성

> 대상: 면접관 / 포트폴리오 설명
> 범위: 왜 장애 처리가 필요한가 → 각 패턴 선택 이유 → 실제 구현 → 트레이드오프

---

## "Node가 느리면 Spring 전체가 죽는다"는 문제에서 시작한다

JackpotChain의 Spring Boot는 거의 모든 API에서 JackpotChain Node의 JSON-RPC를 동기로 호출한다. 대시보드 하나를 그리는 데만 23번의 RPC 호출이 직렬로 일어난다.

이 구조에서 Node가 조금이라도 느려지면 어떤 일이 벌어지는지 생각해보자.

```
시나리오: 블록 처리 중 Node 응답이 30초 걸림

1. 사용자 100명이 동시에 대시보드 접속
2. 각 요청이 Spring 스레드 1개를 점유한 채 Node 응답 대기
3. Spring 기본 스레드 풀(200개)이 순식간에 고갈
4. 새 요청은 큐 대기 → 타임아웃 → HTTP 503
5. Node 장애 하나가 Spring 전체를 다운시킴
```

> **스레드 기아(Thread Starvation):** 모든 스레드가 특정 자원(여기서는 RPC 응답)을 기다리며 점유된 상태. 새 요청을 처리할 스레드가 없어 서비스 전체가 응답 불가 상태가 된다.

이를 막으려면 외부 시스템 장애를 **격리**해야 한다. 장애 처리 패턴들은 각각 다른 레벨에서 이 격리를 구현한다.

## Timeout — 기다림에 끝을 두어야 하는 이유

가장 기본적인 격리는 최대 대기 시간을 설정하는 것이다. Node가 응답하지 않으면 N초 후 강제로 예외를 던지고 스레드를 반환한다.

> **Connect Timeout vs Read Timeout:** Connect Timeout은 TCP 3-way handshake가 완료되기까지의 최대 시간이다. Read Timeout은 연결 후 데이터가 오기까지의 최대 시간이다. 연결은 됐지만 서버가 처리 중이라 응답이 늦는 상황은 Read Timeout이 잡는다.

```java
// JackpotChainHttpRpcClient.java — RPC 클라이언트 설정
HttpComponentsClientHttpRequestFactory factory =
    new HttpComponentsClientHttpRequestFactory();
factory.setConnectTimeout(2000);   // TCP 연결 수립까지 2초
factory.setReadTimeout(5000);      // 응답 데이터 수신까지 5초
```

타임아웃 값은 "경험치"로 정하면 안 된다. Grafana에서 `jackpotchain_rpc_duration_seconds` p95를 측정하고, 그 값의 2~3배로 설정한다. 너무 짧으면 정상 요청이 타임아웃으로 실패하고, 너무 길면 스레드 기아를 막는 효과가 줄어든다.

| RPC 종류 | 권장 타임아웃 | 이유 |
|---|---|---|
| getblockcount, getjackpotpool (조회) | 2~3초 | 빠른 상태 조회, 느리면 캐시 fallback |
| getlottoinfo (탐색 조회) | 3~5초 | 블록 데이터 탐색 시간 고려 |
| sendrawtransaction (TX 제출) | 10~15초 | TX 브로드캐스트 시간 필요 |

## Retry — 모든 실패에 재시도하면 오히려 위험하다

타임아웃 후 자동으로 재시도하면 일시적 네트워크 순단에서 사용자가 에러를 보지 않아도 된다. 그러나 무조건 재시도하면 안 된다.

```
잘못된 예:
sendrawtransaction 실패 → 자동 재시도 3회
→ TX가 이미 mempool에 들어간 상태에서 동일 TX 재전송
→ "already in mempool" 에러 또는 이중 지불 시도
```

> **멱등성(Idempotency):** 동일한 연산을 여러 번 수행해도 결과가 한 번 수행한 것과 같은 성질. GET, PUT, DELETE는 멱등하지만 POST는 기본적으로 멱등하지 않다.

재시도 가능 여부의 핵심 기준은 **멱등성**이다.

| RPC 종류 | 재시도 | 이유 |
|---|---|---|
| 조회성 (getblockcount 등) | O | 여러 번 호출해도 블록체인 상태 변화 없음 |
| TX 제출 (sendrawtransaction) | X | 중복 TX 제출 위험 |
| HTTP 4xx 에러 | X | 요청 자체가 잘못됨 — 재시도해도 동일 |

재시도 간격은 지수적으로 늘려야 한다.

> **Exponential Backoff with Jitter:** 재시도 간격을 지수적으로 증가(1st: 200ms, 2nd: 400ms, 3rd: 800ms)시키되, 무작위 시간을 추가해 여러 클라이언트가 동시에 재시도하는 "Thundering Herd" 문제를 방지하는 전략.

서버가 과부하 상태에서 빠른 재시도는 부하를 더 키울 뿐이다. 간격을 늘려야 서버가 회복할 시간을 준다.

## Circuit Breaker — 연속 실패 시 요청 자체를 차단한다

Retry로도 처리되지 않는 지속적 장애라면, 매 요청마다 타임아웃을 기다리는 것 자체가 낭비다. Circuit Breaker는 전기 차단기처럼 동작한다.

> **Circuit Breaker:** 외부 서비스 호출의 실패율을 집계하다가 임계치를 초과하면 차단기를 열어(OPEN) 이후 요청을 즉시 실패 처리하는 패턴. 서비스 복구 가능성을 탐색하는 HALF_OPEN 상태를 거쳐 자동으로 복구된다.

```
[CLOSED — 정상]
  모든 요청이 Node로 전달됨
  최근 20건 중 실패율 >= 50% → OPEN 전환

[OPEN — 차단]
  요청을 Node로 보내지 않고 즉시 fallback 반환
  (스레드 낭비 없음, Node에 추가 부하 없음)
  30초 후 → HALF_OPEN 전환

[HALF_OPEN — 탐색]
  제한된 요청(5건)만 통과시켜 Node 회복 여부 확인
  성공 → CLOSED 복귀
  실패 → OPEN 재전환
```

OPEN 상태에서 즉시 실패를 반환하는 것이 오히려 사용자 경험에 좋다. 타임아웃 10초를 기다리는 것보다 캐시된 마지막 값을 즉시 받는 것이 낫다.

```java
// Resilience4j 설정
@CircuitBreaker(name = "rpcClient", fallbackMethod = "getBlockCountFallback")
public Long getBlockCount() {
    return rpcClient.invoke("getblockcount", ...);
}

// Circuit OPEN 시 또는 실패 시 호출
private Long getBlockCountFallback(CallNotPermittedException e) {
    return redisTemplate.opsForValue().get("cache:blockcount");  // 마지막 캐시값
}
```

## 멱등키 — 쓰기 요청의 중복을 막는 방법

TX 제출처럼 재시도할 수 없는 쓰기 요청에서 네트워크 타임아웃이 발생하면 난감한 상황이 생긴다. TX가 실제로 제출됐는지 알 수 없는 상태에서 재시도하면 이중 지불 위험이 있고, 재시도를 안 하면 사용자가 에러를 본다.

멱등키는 이 문제를 해결한다. 요청마다 고유한 키를 부여하고, 서버가 동일 키를 처음 처리할 때만 실제 로직을 실행하고 결과를 저장해둔다. 재요청 시에는 저장된 결과를 그대로 반환한다.

```
1회차 요청:
  POST /lotto/commit
  X-Idempotency-Key: uuid-abc-123

  서버: Redis에 "abc-123" 없음 → TX 처리 → Redis에 결과 저장 (TTL 24h)

타임아웃으로 응답을 못 받은 경우:
  POST /lotto/commit (재시도)
  X-Idempotency-Key: uuid-abc-123  ← 동일 키

  서버: Redis에 "abc-123" 있음 → 저장된 결과 그대로 반환 (TX 재처리 없음)
```

멱등키는 요청을 시작하는 프론트엔드가 생성한다. 서버에서 만들면 이미 첫 요청이 서버에 도달한 후이므로 진정한 멱등성이 보장되지 않는다.

## 실제 장애에서 배운 것들

### 지갑 생성 503 — 시작 순서의 중요성

Node가 아직 완전히 기동되지 않은 상태에서 BE가 먼저 올라와 RPC 요청을 보내면 Connection Refused가 발생한다. Docker Compose의 `depends_on: condition: service_healthy`로 Node healthcheck가 통과한 후 BE를 시작하도록 순서를 강제해 해결했다.

> **Healthcheck vs depends_on:** `depends_on: condition: service_started`는 컨테이너가 시작되기만 해도 다음 서비스가 뜬다. `condition: service_healthy`는 `healthcheck` 커맨드가 성공할 때까지 기다린다. 블록체인 Node는 기동 후 체인 로딩까지 수십 초가 걸리므로 healthy 조건이 필수였다.

### 블록체인 동기화 로그 폭발 — 로그 레벨 관리

동기화 중 DEBUG 레벨 로그가 수백만 줄씩 쌓여 디스크를 가득 채웠다. Promtail이 로그를 수집하지 못하고, 컨테이너 로그 볼륨이 호스트 디스크를 잠식했다. 프로덕션에서 DEBUG 로그를 INFO로 올리고, Docker logging driver의 `max-size`와 `max-file`을 설정해 로그 로테이션을 강제했다.

### Webhook 처리 실패 — Scheduler가 안전망

Node → BE Webhook이 실패하면 블록 인덱싱이 누락된다. BlockchainSyncScheduler가 주기적으로 블록 높이를 확인해 누락된 블록을 재처리한다. Webhook은 실시간성을 담당하고 Scheduler는 정확성을 담당하는 이중 구조다. 블록 처리는 같은 높이를 두 번 처리해도 결과가 동일하도록 멱등하게 구현되어 있다.

## 트레이드오프 — 정직하게 말할 것들

**구현 복잡도**: Timeout만으로는 부족해서 Retry를 추가하고, Retry로도 부족해서 Circuit Breaker를 추가하면 코드가 복잡해진다. Resilience4j 어노테이션 조합 시 실행 순서(`@CircuitBreaker` → `@Retry` → 실제 호출)를 정확히 이해해야 한다. 잘못 조합하면 Retry가 Circuit에 3회 실패를 기록해 너무 빨리 OPEN된다.

**Fallback 품질**: Circuit OPEN 시 Redis 캐시를 반환하는 fallback을 만들었는데, 캐시가 오래됐을 수 있다. "최신 데이터" 대신 "직전 데이터"를 보여주는 것이 낫냐, 에러를 보여주는 것이 낫냐는 도메인 맥락에 따라 다르다. 대시보드 조회는 오래된 데이터도 괜찮지만, 잔액 조회는 오래된 데이터가 오해를 줄 수 있다.

**현재 미구현**: 위에서 설명한 패턴들 중 일부(Resilience4j 기반 Circuit Breaker, 멱등키)는 설계 수준에서 검토됐으나 아직 완전히 구현되지 않았다. 현재는 Timeout 설정과 Scheduler 기반 재처리가 주요 방어 수단이다.

## 면접 Q&A

**Q. Timeout, Retry, Circuit Breaker의 역할 차이는?**

각각 다른 레벨의 격리를 담당한다. Timeout은 개별 요청의 최대 대기 시간을 제한한다. Retry는 일시적 실패를 자동으로 재시도한다. Circuit Breaker는 지속적 실패를 감지해 이후 요청이 Node에 도달하지 않도록 차단한다. Timeout 없이 Circuit Breaker만 있으면 Circuit이 OPEN되기 전까지 스레드를 계속 낭비한다. 항상 Timeout → Retry → Circuit Breaker 순으로 쌓는다.

**Q. 왜 TX 제출은 재시도하면 안 되는가?**

블록체인 TX는 네트워크에 브로드캐스트되면 mempool에 들어간다. 타임아웃이 발생했다는 것은 "응답이 늦은 것"이지 "TX가 거부된 것"이 아닐 수 있다. 재시도하면 동일한 UTXO를 두 번 소비하려는 시도가 되어 이중 지불로 처리될 수 있다. 타임아웃 발생 시 "처리 중" 상태로 두고 `getlottoinfo`로 주기적으로 확인하는 것이 안전하다.

**Q. Circuit Breaker의 HALF_OPEN 상태가 왜 필요한가?**

OPEN 상태에서 자동으로 CLOSED로 돌아가면, Node가 회복됐는지 확인 없이 갑자기 모든 트래픽이 쏟아진다. Node가 불안정한 상태라면 즉시 다시 OPEN될 수 있다. HALF_OPEN에서 소수 요청(예: 5건)만 통과시켜 회복 여부를 확인한 뒤 안정적이면 CLOSED로 전환한다. 단계적 트래픽 재개로 Node를 보호하는 것이다.

**Q. Docker healthcheck와 depends_on의 차이는?**

`depends_on: condition: service_started`는 컨테이너 프로세스가 시작됐다는 것만 보장한다. 앱이 초기화 중이어도 다음 서비스가 시작된다. `condition: service_healthy`는 `healthcheck` 커맨드(예: `/actuator/health` HTTP 200 확인)가 성공할 때까지 다음 서비스 시작을 대기한다. JackpotChain Node는 기동 후 체인 로딩까지 수십 초가 걸리므로 `service_healthy`가 필수였다.

**Q. 멱등키는 서버가 만들면 안 되는가?**

서버가 만들면 이미 첫 요청이 서버에 도달한 후다. 만약 요청이 도달하는 과정에서 중복됐다면(예: 클라이언트가 응답을 못 받고 재전송) 두 요청이 서로 다른 키를 받아 둘 다 처리된다. 클라이언트가 요청을 생성하는 시점에 키를 만들어야 동일 사용자 행동에서 발생한 모든 재시도가 같은 키를 공유한다.

**Q. 멱등키를 Redis에 24시간 보관하는 이유는?**

짧으면 사용자가 재시도할 수 있는 시간 내에 키가 만료돼 다시 중복 처리될 수 있다. TX 처리 후 사용자가 재시도할 가능성이 있는 시간(네트워크 오류, 페이지 새로고침 등)을 커버해야 한다. 24시간은 일반적인 사용자 행동 패턴에서 충분한 시간이다. 너무 길면 Redis 메모리를 낭비하므로, 도메인 특성에 맞게 조정한다.
