## "7초짜리 대시보드"에서 시작한다

성능 테스트를 하기 전까지는 서비스가 "느리다"는 걸 알아도 어디가, 왜 느린지 정확히 몰랐다. 막연히 "캐시를 붙이면 되겠지"라는 생각이 있었지만, 실제로 측정해보니 예상보다 훨씬 심각한 상황이었다.

baseline 측정 결과, 대시보드 API의 p95 응답 시간이 **7,689ms**였다. 목표는 500ms다. 15배 차이다. 원인을 분석해보니 단일 요청이 RPC를 **23번 직렬로** 호출하고 있었다.

```
GET /api/v1/blockchain/dashboard 1건 처리 시:

getBlockchainInfo()             → RPC 1회
getPeerInfo()                   → RPC 1회
getMempoolTransactionCount()    → RPC 1회
getBlockHash(height) × 10      → RPC 10회  (최근 10개 블록 해시)
getBlock(hash)       × 10      → RPC 10회  (각 블록 데이터)
                                  합계: 23회 (직렬, 캐시 없음)
```

각 RPC 호출이 평균 300ms라면 23번이면 약 7초다. 캐시도 없고, HTTP 연결 풀도 없었다.

## 왜 k6를 선택했는가

성능 테스트 도구로 nGrinder, JMeter, k6 중 k6를 선택했다.

> **k6:** Grafana Labs가 개발한 오픈소스 부하 테스트 도구. JavaScript(ES6)로 시나리오를 작성하며 Docker 이미지로 배포 가능하다. Prometheus remote write를 지원해 테스트 중 메트릭을 실시간으로 Grafana에서 볼 수 있다.

| 기준 | k6 | nGrinder | JMeter |
|---|---|---|---|
| 시나리오 언어 | JavaScript (ES6) | Groovy/Python | XML (.jmx) |
| Docker 지원 | 공식 이미지 제공 | 별도 구성 필요 | 별도 구성 필요 |
| Prometheus 연동 | native 지원 | 없음 | 플러그인 필요 |
| 학습 곡선 | 낮음 | 중간 | 중간 |

k6를 선택한 결정적 이유는 **이미 쓰고 있는 Grafana/Prometheus와 자연스럽게 연동**되기 때문이다. 테스트 중 응답 시간 추이와 HikariCP pending 연결 수를 같은 대시보드에서 실시간으로 볼 수 있다.

```bash
# Prometheus remote write로 k6 메트릭을 실시간 수집
k6 run --out=experimental-prometheus-rw \
  -e K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
  -e BASE_URL=http://localhost:13000 \
  perf/k6/baseline_read.js
```

## 시나리오 설계 — 블록체인 TX의 특수성

읽기 시나리오와 쓰기 시나리오는 executor를 다르게 설정했다.

> **Executor (k6):** 가상 유저(VU)가 어떤 방식으로 요청을 생성할지 결정하는 설정. `constant-vus`는 N명이 계속 요청을 보내고, `shared-iterations`는 N명이 총 M번의 요청을 나눠서 처리한다.

```javascript
// perf/k6/baseline_read.js — 읽기 시나리오
export const options = {
  scenarios: {
    dashboard: {
      executor: "constant-vus",    // 100명이 5분 내내 계속 요청
      vus: 100,
      duration: "5m",
      exec: "dashboardScenario",
    },
    lotto_overview: {
      executor: "constant-vus",
      vus: 50,
      duration: "5m",
    },
  },
  thresholds: {
    "http_req_duration{scenario:dashboard}": ["p(95)<500"],  // 합격 기준
    custom_errors: ["rate<0.01"],
  },
};
```

쓰기 시나리오(POST /lotto/commit)는 `shared-iterations`를 써야 했다.

```javascript
// perf/k6/baseline_commit.js — 쓰기 시나리오
export const options = {
  scenarios: {
    lotto_commit: {
      executor: "shared-iterations",  // 20명이 총 payloads.length번 나눠서 처리
      vus: 20,
      iterations: payloads.length,
      maxDuration: "10m",
    },
  },
};
```

`constant-vus`를 쓰면 동일한 signed TX를 반복 전송하게 되는데, 블록체인 TX는 한 번 mempool에 들어가면 재전송이 거부된다. UTXO는 한 번만 소비할 수 있다. 따라서 사전에 서로 다른 signed TX를 N개 준비해두고, 각 VU가 하나씩 소비하는 `shared-iterations` 방식을 써야 했다.

> **Pre-signed TX:** 서명이 완료된 직렬화된 트랜잭션 hex. 서명은 클라이언트 측 개인키로 수행되므로 테스트 전에 미리 생성해 fixtures에 저장해둔다. 각 TX는 서로 다른 UTXO를 소비하므로 중복 없이 한 번씩만 제출 가능하다.

## 개선 단계 설계

병목을 정확히 알았으므로 개선을 단계별로 설계하고 각 단계마다 측정했다.

### Step 0: 토큰 재발급 (테스트 선행 조건)

JWT 만료 문제를 해결하는 스크립트를 먼저 만들었다. 테스트 직전에 항상 실행해 15분 TTL 내에 테스트가 완료되도록 한다.

```python
# perf/setup/refresh_tokens.py (신규 작성)
for w in wallets:
    priv = bytes.fromhex(w["privateKeyHex"])
    pub  = bytes.fromhex(w["publicKeyHex"])
    new_token = get_access_token(base_url, w["address"], priv, pub)
    w["accessToken"] = new_token

Path("perf/fixtures/test-wallets.json").write_text(json.dumps(wallets, indent=2))
```

### Step 1: HikariCP 커넥션 풀 확장

200 VU가 동시에 접근할 때 DB 연결 10개는 부족하다.

```yaml
# application-local.yml
hikari:
  maximum-pool-size: 10 → 30   # 200 VU × DB 접근 비율 고려
  connection-timeout: 3000 → 5000
```

### Step 2: RPC HTTP 연결 풀 적용

요청마다 새 TCP 소켓을 만드는 것 → 연결 풀로 재사용.

```java
// Before: 요청마다 새 TCP 소켓
SimpleClientHttpRequestFactory

// After: 최대 300개 연결 풀
PoolingHttpClientConnectionManager cm = new PoolingHttpClientConnectionManager();
cm.setMaxTotal(300);
cm.setDefaultMaxPerRoute(300);  // Node 1개 대상이므로 전체와 동일
HttpComponentsClientHttpRequestFactory factory =
    new HttpComponentsClientHttpRequestFactory(httpClient);
```

기대 효과: 연결 오버헤드 수십ms 제거 → dashboard p95 약 3,000~5,000ms 예상.

### Step 3: Redis 캐싱 (핵심 개선)

블록 데이터는 불변이다. 한 번 확정된 블록의 해시와 내용은 절대 바뀌지 않는다. 매 요청마다 RPC로 가져올 이유가 없다.

```java
// @Cacheable 적용
@Cacheable(value = "blockHash", key = "#height")   // TTL 10분 (불변 데이터)
public String getBlockHash(long height) { ... }

@Cacheable(value = "block", key = "#blockHash")    // TTL 10분
public JackpotChainBlock getBlock(String blockHash) { ... }

@Cacheable(value = "jackpotPool", key = "'global'") // TTL 5초 (블록마다 변경)
public JackpotChainJackpotPool getJackpotPool() { ... }

@Cacheable(value = "dashboard", key = "#limit")    // TTL 3초
public BlockchainDashboardResponse getDashboard(int limit) { ... }
```

기대 효과: 캐시 히트 시 RPC 23회 → 0회. dashboard p95: 7,689ms → **10~50ms 예상**.

> **Cache Stampede:** 캐시 TTL이 만료된 직후 여러 요청이 동시에 Cache Miss를 경험해 모두 백엔드(RPC)로 향하는 현상. 한 번에 많은 요청이 RPC를 동시에 호출해 오히려 과부하가 걸릴 수 있다. 해결책: 분산 락(한 요청만 RPC 호출, 나머지 대기) 또는 probabilistic early expiration(만료 전 확률적으로 미리 갱신).

### Step 4: RPC 병렬 호출 (조건부)

Step 3으로 p95 < 500ms를 달성하지 못할 경우에만 진행. 캐시 Cold Start 시 직렬 10회 RPC를 병렬로 변환.

```java
// Before: for 루프 직렬
for (long height = startHeight; height <= currentHeight; height++) {
    String hash = rpcClient.getBlockHash(height);
    JackpotChainBlock block = rpcClient.getBlock(hash);
}

// After: CompletableFuture 병렬
List<CompletableFuture<...>> futures = LongStream
    .rangeClosed(startHeight, currentHeight)
    .mapToObj(height -> CompletableFuture.supplyAsync(() -> {
        String hash = rpcClient.getBlockHash(height);
        return rpcClient.getBlock(hash);
    }))
    .toList();

CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
```

## 성능 지표 해석 — 무엇을 봐야 하는가

> **p95 (95th percentile):** 전체 요청 중 하위 95%가 이 시간 내에 완료됐다는 의미. 즉 상위 5%의 느린 요청을 제외한 기준선이다. SLA(서비스 수준 협약)에 자주 사용된다.

평균(avg)만 보면 안 되는 이유: 대부분 요청이 10ms이고 일부가 10,000ms면 평균은 100ms처럼 보이지만 실제 사용자 10%는 10초를 기다린다. p95, p99가 실제 사용자 경험을 더 잘 반영한다.

| 지표 | 의미 | 이 프로젝트 기준 |
|---|---|---|
| avg latency | 전체 평균 — 경향 파악 | 참고용 |
| p95 latency | 95% 요청의 응답 시간 | GET: 500ms, POST commit: 1000ms |
| p99 latency | 99% 요청 — 최악 케이스 | 경보 기준 |
| TPS | 초당 처리 요청 수 | 병목 전 포화점 확인 |
| error rate | 실패 비율 | 1% 미만 |

```
TPS 곡선: VU가 늘어날수록 TPS가 증가하다가 포화점에서 수평
     TPS
      │         ●●●●●●●● ← 포화점 (병목 도달)
      │      ●●
      │   ●●
      │●●
      └─────────────────── VU 수

포화점 이후 VU를 더 늘리면 TPS는 그대로지만 에러율과 latency만 증가한다.
```

## 트레이드오프 — 정직하게 말할 것들

**캐시 TTL의 딜레마**: TTL을 짧게 하면 신선한 데이터를 보장하지만 RPC 부하가 줄지 않는다. TTL을 길게 하면 RPC 부하는 줄지만 데이터가 오래됐을 수 있다. 블록 데이터는 불변이므로 길게 해도 무방하지만, 잭팟 풀 잔액 같은 동적 데이터는 사용자에게 잘못된 정보를 줄 수 있다. 새 블록 Webhook 수신 시 관련 캐시를 evict하는 방식으로 일관성을 보장한다.

**k6 shared-iterations의 한계**: Pre-signed TX를 미리 준비해야 하는 번거로움이 있다. TX 수가 곧 테스트 규모의 상한이 된다. 10,000회 commit 테스트를 하려면 10,000개의 pre-signed TX와 그에 해당하는 UTXO가 필요하다. 로컬 테스트 환경에서 UTXO를 그만큼 준비하기 어렵다.

**JWT TTL 제약**: access token TTL이 15분이므로, 토큰 재발급 후 15분 이내에 테스트를 완료해야 한다. 긴 테스트나 여러 단계를 연속으로 실행할 때 중간에 토큰이 만료될 수 있다. 테스트 전용 long-lived token 발급 엔드포인트가 있으면 편하지만, 보안 정책과 충돌한다.

## 면접 Q&A

**Q. k6를 선택한 이유는?**

Prometheus remote write를 native하게 지원해서 테스트 중 k6 메트릭과 Spring Boot 메트릭(HikariCP, JVM)을 동일한 Grafana 대시보드에서 실시간으로 볼 수 있었습니다. "응답이 느린 순간에 HikariCP pending이 얼마나 올라가는가"를 같은 타임라인에서 확인할 수 있어 병목 원인 분석이 빨랐습니다. 또한 JavaScript 기반이라 별도 언어 학습 없이 시나리오를 작성할 수 있었습니다.

**Q. constant-vus와 shared-iterations의 차이는?**

`constant-vus`는 N명의 VU가 테스트 시간 동안 계속 반복해서 요청을 보냅니다. `shared-iterations`는 N명이 총 M번의 작업을 나눠서 한 번씩 처리하면 종료됩니다. 블록체인 TX는 동일한 TX를 재전송할 수 없으므로, M개의 사전 준비된 TX를 20명이 한 번씩 소비하는 shared-iterations를 써야 했습니다. 일반 읽기 API는 중복 없이 반복 호출이 가능하므로 constant-vus를 씁니다.

**Q. dashboard p95가 7,689ms인 근본 원인은?**

단일 요청 처리에 RPC 23번이 직렬로 실행됐고, HTTP 커넥션 풀 없이 요청마다 TCP 소켓을 새로 생성했습니다. RPC 1회당 평균 300ms라 하면 23회면 6.9초입니다. Redis 캐싱을 적용하면 캐시 히트 시 RPC 호출이 0으로 줄어 10~50ms 수준이 될 것으로 예상했습니다.

**Q. p95와 평균(avg) 중 어느 것이 더 중요한가?**

p95가 더 중요합니다. 평균은 극단적인 이상값의 영향을 받으며, 대다수 요청이 빠르더라도 일부가 매우 느리면 평균이 왜곡됩니다. SLA는 보통 "p95 < N ms"로 정의합니다. 5%의 사용자가 느린 경험을 하는 것도 많은 수의 사용자에게는 영향을 미치기 때문입니다. 이 프로젝트의 목표도 "p95 < 500ms"로 설정했습니다.

**Q. Cache Stampede는 어떻게 방지하는가?**

TTL이 만료된 직후 대량의 요청이 동시에 Cache Miss → RPC 호출로 이어지는 문제입니다. 두 가지 방법이 있습니다. 첫 번째는 분산 락: 첫 번째 요청만 RPC를 호출하도록 Redis 락을 잡고, 나머지는 첫 번째 요청이 캐시를 채울 때까지 대기합니다. 두 번째는 TTL 만료 전 미리 갱신: Webhook으로 새 블록이 오면 TTL 만료를 기다리지 않고 캐시를 즉시 evict합니다. 이 프로젝트는 새 블록 Webhook 수신 시 `@CacheEvict`로 관련 캐시를 evict하는 방식을 채택했습니다.

**Q. 성능 개선 결과를 어떻게 수치로 증명하는가?**

각 개선 단계 전후에 동일한 조건(동일 VU, 동일 duration, 토큰 재발급)으로 k6를 실행하고 결과를 `perf/docs/plan.md`에 단계별로 기록합니다. Prometheus에 저장된 메트릭으로 개선 전후의 RPC 호출 수, cache hit ratio, HikariCP pending 변화를 Grafana 스크린샷으로 남깁니다. 숫자 없는 "최적화했다"는 주장은 증명이 아닙니다.
